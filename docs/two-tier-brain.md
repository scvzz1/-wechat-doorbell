# 可选方案：双档大脑（值班小 bot + 本人唤醒）

> **状态：设计文档，未随附实现。**
> 作者本人在自己的生产环境认真评估过这套方案，最终**没有采用**
> （原因写在最后一节）。把它公开出来，是因为否决理由很主观——
> 换个使用场景，它可能正是对的解。欢迎按此设计自行实现，或提 PR。

## 它解决的问题

门铃架构的固有代价是延迟：轮询间隔＋ agent 冷启动，回复通常在
十几到几十秒量级。可现实里一半以上的消息是"在吗""好的""这个表情
什么意思"——为这种消息把全量 agent 唤醒一遍，又慢又浪费。

双档大脑的思路：**在收件箱和大脑之间加一层分诊**。

```
inbox.jsonl ──▶ 分诊小 bot（便宜、快、常驻）
                  ├─ 简单消息 ──▶ 自己秒回（1~3 秒）
                  └─ 复杂消息 ──▶ 先垫一句"收到，我想想"
                                   └─▶ 唤醒全量 agent ──▶ 本人详回
```

## 分诊怎么判

小 bot 只做判断（外加答简单题），判据示意：

- **自己答**：闲聊寒暄、确认类（好的/收到）、格式固定的查询
  （时间、天气、已公开的信息）、不需要长期记忆的问题；
- **转本人**：涉及用户的计划、文件、账号、记忆与关系上下文；
  需要动手执行的任务；长内容、多步骤、拿不准的一切问题。
- 原则：**拿不准就转本人**。分诊的错误成本不对称——闲聊答错无伤
  大雅，该转的没转才会坏事。

## 配套机制：攒波

用户连发多条时，先等一个静默窗口（建议 5~10 秒），把这一波消息
合并后再分诊。既避免小 bot 抢答半截话，也减少全量 agent 的唤醒次数。
这一条与双档无关，单独用在门铃 hook 上也成立。

## 小 bot 以什么身份出现：三案

分诊最难的不是技术，是**身份**——同一个微信窗口里出现"两个说话者"，
违和感从哪来、怎么处理，有三种摆法：

- **甲案 · 共用窗口**：小 bot 就在同一个联系人窗口里说话，用口吻或
  前缀区分（比如值班式语气）。优点：单入口、无感切换；
  缺点：**身份割裂**——顶着同一个头像和名字，却是另一个"人格"在答话。
- **乙案 · 独立门户**：小 bot 挂另一个微信号，作为独立联系人存在。
  优点：身份干净，谁是谁一目了然；缺点：用户要先选"跟谁说"。
  注意本仓库的实测结论「一号一活 bot」：一个微信号同时只能存活一个
  bot，所以乙案必然占用第二个微信号。
- **丙案 · 留言板模式**：小 bot 从不"冒充回复"，只做接单登记
  （"收到，已转达"），所有实质回复都等本人。配套**本人在线租约**：
  本人每次回复时续租一个时效文件（比如 10 分钟），租约有效期内
  小 bot 完全静默，防止两个说话者抢话。

## 成本与延迟（量级示意）

| | 简单消息 | 复杂消息 |
|---|---|---|
| 纯门铃（默认方案） | 唤醒全量 agent，十几~几十秒 | 同左 |
| 双档（本方案） | 小 bot 秒回，1~3 秒；成本约一次小模型调用 | 垫话秒到＋本人随后详回 |

## 适用 / 不适用

- **适合**：消息量大、闲聊占比高的号；客服式、团队共用的号；
  对延迟敏感、对"人格唯一性"不敏感的场景。
- **不适合**：追求"微信那头自始至终是同一个有记忆的本人"体验的
  个人号——这正是作者的场景。

## 作者为什么最终没用

一句话：**这套桥的全部意义就是"本人"，甲案的割裂感动摇了这个根基；
乙案要多养一个号、丙案则把"秒回"退化成"秒登记"，收益不够抵偿复杂度。**
加上作者的消息量不大，几十秒延迟完全可接受，于是砍掉，双档只留
"攒波"的思想用在别处。你的场景若不同，结论可以完全相反。

## 实现指引（给动手的人）

在 `brains/` 层实现即可，桥本体不用改：

1. 分诊器：一个常驻小进程轮询 `inbox.jsonl`（可复用
   `brains/brain_command.py` 的骨架），用便宜模型做分类＋简答；
2. 转本人通道：把复杂消息落成一个"唤醒队列"文件，门铃 hook 或
   `brain_command.py` 盯这个队列唤醒全量 agent；垫话由分诊器先发，
   注意在 `sent.jsonl` 里区分"垫话"与"正式回复"，防去重逻辑误杀；
3. 租约：丙案的租约文件放桥目录下，约定路径与时效，双方都只读/续写
   这一个文件，不要另设状态。
